=== time zones in deal scheduling
A deal's start date is a bare `DATE`, and "today" means a different day on each side. The front end
takes it from the vendor's browser (`todayIso` in `scheduleDates.ts`) to grey out past days and to refuse
a past start before saving. The backend takes it from the server's default zone, through `@FutureOrPresent`
on `DealPayload.Schedule`, `DealSubmissionRules` on submit and `PublicDealService` when it decides which
deals are running. Near midnight the two disagree: a vendor in UTC-5 choosing today's date late in the
evening is refused by a server on UTC, which has already moved on to tomorrow. And a deal starts and ends
on the server's midnight, not the vendor's or the visitor's.

Decide which calendar a deal runs on - one platform zone, configured rather than the JVM default, or the
vendor's zone stored on the deal - and use that zone for every "today" on both sides. Until then, accepting
a start date one day behind the server's would at least stop vendors west of the server from being
refused a date their own calendar offered.

=== talent signals the schema has nowhere to put
`/api/talent/browse` serves the half of the directory's sidebar that has columns behind it - skills,
languages, workplace, employment type, location, relocation and text. The other half is rendered disabled
on the front end, with its stand-in values quarantined in `src/components/talent/placeholders.ts`. The
same file now also feeds the public profile page, which draws the badges, the availability dot, the years
of experience, the industries row and a last-updated date whether or not anything backs them:

* verified and featured - the same gap as tools; see "featured and trending signals"
* industries and talent tags - tools have a `tags` JSONB, talent has neither column nor vocabulary
* years of experience - `talent_experience.period` is free text like "2021 - Present", so it is neither

* last updated - `talent_profile` records `created_at` only, so the profile page's "Updated" line is
  derived from the creation date rather than from anything that tracks edits
* daily rates - the rate insights section on the profile page is entirely front-end mock; nothing collects

Also: `work_employment_type` is a single VARCHAR while the directory's design treats engagement types as a

less when the only public listing was a catalogue of products.

=== persist the lucene index
`LuceneIndexManager` builds a `ByteBuffersDirectory`, so the index lives in the heap, dies with the JVM
and cannot be shared between nodes - every restart serves nothing until `SearchIndexBootstrap` has
rebuilt it. `/api/tool/browse` was written not to depend on it for filtering, counting or paging for that
reason, but the text query still does.

=== filters written into the search input
The original todo in `DocumentSearchService.search(SearchRequest)`: let the query itself carry filters,
`#cat:coding` and the like. `addExactTagFilters` and `buildCategoryQuery` are already written there and
already unreachable - no endpoint calls the overloads that use them. The front page search bar already
parses `#cat:` client-side and turns it into a category parameter, so the two need to agree on the syntax.

=== validate submitted categories against the category table
`VendorOnboardingService` writes whatever categories the payload carries straight into
`tool_submission.categories` as free text. The `category` table is now seeded and is what the directory
filters on, so a typo or a stale front-end list silently produces a tool nobody can filter to - which is
exactly how the front end ended up with two disagreeing category lists. `tool_submission_category` is
the join table for this and is still never written to.
